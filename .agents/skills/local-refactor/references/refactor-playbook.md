# Whole-App Refactoring — Architecture, Layer Separation & Extensibility

## 1. 角色与目标

你是一名资深软件架构师，负责对当前 App 进行一次有计划、可验证、渐进式的系统重构。

当前项目约 10,000 行代码，存在面条代码、业务逻辑与视图逻辑混杂、职责边界不清晰等问题。

本次重构的目标不是简单地拆分文件、统一命名或追求代码风格，而是建立一套适合该项目长期演进的代码架构：

1. **分离数据层与视图层**：视图负责展示和用户交互，不直接承担数据访问、持久化或复杂业务规则。
2. **提取业务逻辑**：将散落在页面、回调、事件处理器中的业务规则集中到具有明确职责的模块中。
3. **识别并抽象稳定概念**：对重复出现、语义一致、具有独立职责的逻辑建立可复用抽象。
4. **控制抽象成本**：不为每个函数、类或数据结构强行增加接口、基类或设计模式。
5. **为扩展留出合理空间**：隔离易变化的实现细节，为有证据支持的变化点提供扩展能力，而不是提前构建通用框架。
6. **保持功能兼容**：除非明确批准改变行为，否则重构前后应保持用户可观察到的行为一致。
7. **提高可测试性与可维护性**：使业务规则能够脱离 UI 独立测试，使模块的使用方式不需要了解其内部实现。

最终结果应当是一套结构清晰、职责明确、依赖方向合理、易于理解和扩展的代码，而不是单纯增加文件数量。

## 2. 核心原则

### 2.1 先理解现有系统，再设计目标架构

不得在没有充分了解项目的情况下直接套用 MVC、MVVM、Clean Architecture、Hexagonal Architecture 或其他架构模板。

先检查：

- 项目使用的语言、UI 框架、运行时和构建工具。
- App 的入口、页面组织方式、导航机制和生命周期。
- 数据来源、数据存储、缓存、状态管理和异步处理方式。
- 核心业务流程以及它们之间的调用关系。
- 外部 API、文件系统、数据库、系统服务和第三方 SDK。
- 现有测试、配置、文档以及项目的实际依赖关系。

根据真实代码决定采用何种分层和模块结构。

可以借鉴成熟架构，但必须说明它解决了当前项目中的什么具体问题。

### 2.2 以模块职责为中心，而不是以文件数量为中心

一个模块应当具有：

- 明确且集中的职责。
- 简洁、稳定的公开接口。
- 隐藏在接口后面的内部实现。
- 清晰的输入、输出、错误语义和状态约束。
- 可独立验证的行为。

优先把复杂行为收敛到职责明确的模块内部，而不是把一段逻辑拆成多个文件后，仍然要求调用方理解所有实现细节。

采用以下判断标准：

**如果移除某个模块后，原有复杂度只是扩散到所有调用方，那么这次抽象没有真正解决问题。**

### 2.3 渐进式重构，避免整体重写

- 每个阶段都应当形成可审查、可验证的增量。
- 优先选择边界清晰、收益明确、风险可控的重构单元。
- 尽量通过局部迁移逐渐改变依赖关系。
- 不同时进行大规模架构调整、业务规则修改和依赖升级。
- 不得因为目标架构更漂亮，就直接废弃仍然承担业务职责的现有实现。
- 不得以项目规模较小为理由，忽略测试、回滚和兼容性。

## 3. 阶段一：全项目考察与架构审计

本阶段只读，不修改业务代码。

### 3.1 建立项目地图

扫描整个项目，而不是只阅读入口文件或最近修改的几个文件。

识别并记录：

- 主要目录、模块、文件及其职责。
- 页面、组件、状态对象和事件处理器。
- 数据访问、序列化、缓存和持久化逻辑。
- 业务规则、计算逻辑和数据转换。
- 跨模块调用、共享状态、全局对象和隐式依赖。
- 重复实现、超大文件、超大函数和复杂条件分支。
- 现有抽象以及它们是否真正被使用。
- 高频变更文件与复杂度集中的区域。

使用适合当前语言的静态分析、搜索、调用关系分析、测试和构建工具辅助调查。

不要仅根据文件名推断职责。必须检查实际实现和调用方。

### 3.2 绘制当前架构

至少输出：

1. 当前模块职责图。
2. 主要依赖关系图。
3. 典型业务流程的数据流和调用链。
4. 数据从输入到存储、处理、展示的完整路径。
5. UI 与业务逻辑、数据访问之间的耦合点。
6. 全局状态和共享可变状态的使用情况。

明确指出复杂度实际存在的位置，以及复杂度为什么会在不同模块之间传播。

### 3.3 建立问题清单

每个问题必须包含：

- 唯一编号。
- 涉及文件和准确的代码位置。
- 当前职责或依赖关系。
- 可复核的代码证据。
- 对维护、测试、扩展或可靠性的实际影响。
- 推荐的调整方向。
- 实施成本与回归风险。
- 置信度及尚未确认的假设。

重点检查：

- 视图层直接操作数据库、文件或远程 API。
- UI 回调中包含复杂业务规则。
- 同一业务规则在多个页面中重复实现。
- 数据模型同时承担持久化、业务计算和展示格式转换。
- 一个模块同时负责导航、状态管理、数据访问和业务编排。
- 跨模块直接修改内部状态。
- 依赖全局单例、静态变量或隐式生命周期的代码。
- 为复用而产生的复杂通用工具或过度抽象。
- 没有明确职责、没有真实调用价值的接口与包装层。
- 错误处理、异步执行、资源释放和状态更新中的潜在问题。

不得为了让报告显得完整而强行列出问题。合理的现有设计应当被保留。

### 3.4 建立行为基线

在提出具体重构方案之前：

- 识别现有可运行的测试、构建和静态检查。
- 运行当前项目已有的验证流程。
- 记录失败的测试、构建问题及环境限制。
- 为核心业务流程确定可观察的行为和关键不变量。
- 识别当前缺少测试、无法直接验证的区域。

对于难以测试的遗留逻辑，提出补充特征测试（Characterization Tests）的计划，记录现有实现的实际行为。

不得假设现有代码完全正确，也不得把既有 Bug 自动认定为必须保留的设计。

## 4. 阶段二：设计目标架构

根据审计结果提出目标架构，先说明职责与依赖，再决定目录和文件。

### 4.1 数据层与视图层分离

明确区分以下职责，并根据项目实际需要合并或细分模块：

**Presentation / UI**

负责：

- 展示界面。
- 接收用户输入。
- 展示加载、成功、空状态和错误状态。
- 将用户意图交给业务层。
- 将业务结果映射为界面状态。

不应直接承担复杂业务规则、数据持久化或外部服务调用。

**Application / Use Cases**

负责：

- 编排完整业务操作。
- 协调多个业务模块或数据访问模块。
- 管理业务操作的执行顺序。
- 定义必要的事务边界和失败处理策略。

仅在项目确实存在相应复杂度时引入，不要为简单操作机械创建大量 UseCase 类。

**Domain / Business Logic**

负责：

- 稳定的业务规则。
- 业务计算与决策。
- 必要的领域对象和不变量。
- 与具体 UI、数据库及外部 SDK 无关的核心行为。

不要把纯数据结构全部升级成复杂的领域模型。抽象的复杂度必须与业务价值匹配。

**Data / Infrastructure**

负责：

- 数据获取、存储和更新。
- 数据源访问、缓存和持久化。
- 网络请求、文件操作及第三方服务适配。
- 数据格式转换和底层错误映射。
- 数据访问实现的生命周期与资源管理。

根据实际需求确定 Repository、Data Source、Adapter 等接口与实现。

### 4.2 定义依赖方向

设计并验证依赖规则：

- UI 依赖稳定的业务操作或状态接口，而不是具体的数据存储实现。
- 业务规则不直接依赖具体 UI 框架。
- 业务层需要抽象外部能力时，由具体实现适配该抽象。
- 数据访问细节不应泄漏到所有业务调用方。
- 跨模块共享的数据类型应有明确的归属。
- 不得通过全局事件总线、Service Locator 或万能管理器掩盖真实依赖。

不要求每一层都必须存在。如果某项抽象没有明确收益，可以保留更简单的结构。

### 4.3 设计状态与数据流

明确区分：

- 持久化数据。
- 业务计算过程中的临时状态。
- 页面展示状态。
- 用户输入和未提交编辑状态。
- 可重新计算的派生数据。
- 缓存数据及其失效规则。

明确每类状态的唯一权威来源、所有者、更新入口和生命周期。

避免同一份数据被 UI、业务层和数据层分别维护多个可变副本。

对于异步操作，明确加载、成功、失败、取消和重复请求的处理方式。保留当前系统必要的并发和顺序语义。

### 4.4 识别值得抽象的稳定概念

对现有代码中的重复逻辑进行分类，而不是简单执行文本级去重。

优先考虑抽象的对象包括：

- 多处重复且语义一致的业务规则。
- 具有相同不变量的数据处理流程。
- 被多个页面使用且职责明确的业务能力。
- 重复出现的外部依赖访问模式。
- 多个实现之间存在稳定共同契约的变化点。
- 能够隐藏显著复杂度的模块。

每个抽象必须回答：

1. 它代表什么业务概念或技术职责？
2. 哪些现有实现应该归入其中？
3. 哪些行为必须保持一致？
4. 它向调用方提供什么最小接口？
5. 它隐藏了哪些实现细节？
6. 为什么把逻辑集中起来比让调用方自行组合更好？
7. 如果未来需要修改实现，哪些调用方可以保持不变？

只有名称相似、偶然结构相似或尚未证实语义一致的代码，不应强行合并。

### 4.5 为扩展性留出空间

扩展性应建立在真实的变化需求和清晰的职责边界之上。

优先使用：

- 稳定的模块接口。
- 明确的数据契约。
- 必要的策略替换点。
- 具体实现与调用方之间的适配层。
- 集中管理的配置和能力注册机制（仅在确有需求时）。
- 能够独立测试的业务规则。

以下情况才考虑引入接口、策略模式、工厂或插件机制：

- 已存在多个真实实现。
- 已知需求明确要求替换实现。
- 变化频率高，而调用方应保持稳定。
- 存在明确的外部依赖隔离需求。

不得仅因为“未来可能扩展”就引入抽象工厂、通用事件总线、插件系统、复杂依赖注入框架或多层代理。

**优先满足已知需求，并为合理可预见的变化保留最小扩展点；不为无法描述的未来需求设计通用框架。**

### 4.6 提出候选架构与迁移方案

输出：

- 推荐的目标模块图。
- 各模块的职责、公开接口与禁止承担的职责。
- 关键依赖方向。
- 核心数据流和状态流。
- 需要新建、合并、拆分或迁移的模块。
- 现有代码与目标架构之间的映射关系。
- 需要保留的兼容层及其退出条件。
- 采用该架构的具体理由。
- 不选择其他方案的原因。
- 目标架构的复杂度成本与潜在缺点。

优先考虑清晰、浅层、职责集中的模块，而不是追求层数更多、接口更多或设计模式更多。

## 5. 阶段三：制定可执行的重构路线图

将整个重构拆成多个可独立审查的阶段。

推荐顺序如下，但必须根据实际依赖关系调整。

### Phase 0 — 基线与风险控制

- 确认当前工作区状态。
- 记录已有测试与构建基线。
- 补充关键业务流程的行为测试。
- 标记高风险模块、外部契约和无法充分验证的区域。

### Phase 1 — 切断最严重的职责混杂

- 选择复杂度高且边界明确的业务流程。
- 将数据访问从 UI 中迁出。
- 将核心业务规则从事件处理器中迁出。
- 建立最少必要的模块接口。
- 保持原有调用入口可用，降低一次性迁移风险。

### Phase 2 — 提取稳定业务抽象

- 合并语义一致的重复逻辑。
- 统一重复出现的数据转换和业务规则。
- 为共享能力定义清晰的接口。
- 消除不必要的跨模块状态修改。
- 保留确有差异的实现，不进行过度统一。

### Phase 3 — 整理状态、依赖和生命周期

- 明确数据的所有者和权威来源。
- 清理隐式依赖和不必要的全局状态。
- 规范异步操作、错误处理及资源生命周期。
- 根据实际需求隔离外部依赖。

### Phase 4 — 收尾与清理

- 删除已确认不再使用的旧实现。
- 移除过渡适配层，或记录暂时无法移除的原因。
- 清理不再需要的依赖和重复工具。
- 更新架构文档与模块说明。
- 完成最终的测试、构建与独立代码审查。

每个阶段必须明确：

- 修改范围。
- 前置条件。
- 预期收益。
- 风险及依赖。
- 具体任务与完成标准。
- 需要运行的验证命令。
- 回滚策略。

不要预先承诺不切实际的工期，也不要把所有文件都列入重构范围来制造工作量。

## 6. 阶段四：按模块执行重构

只有在目标架构与路线图获得批准后，才能进入执行阶段。

### 6.1 每次只处理一个明确的重构单元

一个重构单元可以是一个业务流程、一个职责混杂的模块，或一组具有明确依赖关系的文件。

每次执行：

1. 阅读涉及模块的完整实现和所有重要调用方。
2. 明确该单元的旧职责、目标职责和行为约束。
3. 确认需要补充或运行的测试。
4. 先完成最小的结构调整，再考虑后续优化。
5. 更新调用方，使其依赖新的稳定接口。
6. 运行相关测试、静态检查和构建。
7. 检查实际 diff，确认没有混入无关修改。
8. 记录已完成内容、未完成事项和剩余风险。

一个重构单元完成并通过验证后，才能继续下一个。

### 6.2 优先采用可逆的结构变换

优先考虑：

- 提取函数或模块。
- 将数据访问迁移到数据层。
- 将业务逻辑迁移到业务模块。
- 通过薄适配层保持原有调用接口。
- 逐步切换调用方到新的实现。
- 在确认没有剩余依赖后删除旧代码。

不要同时大规模修改数据结构、业务规则、外部接口和 UI 行为。

当需要更改公开接口时，先列出所有调用方、兼容策略和迁移顺序。

### 6.3 每次修改后进行独立审查

审查者必须能够独立阅读实际 diff，并验证：

- 是否确实改善了职责边界。
- 是否引入了多余的抽象或间接调用。
- 是否仍然存在原来的数据层与视图层耦合。
- 是否引入循环依赖或反向依赖。
- 是否改变了业务行为、错误语义或数据顺序。
- 是否遗漏异步取消、重复请求、状态同步或资源释放。
- 是否删除了仍可通过动态调用、路由、配置或注册机制访问的代码。
- 测试是否验证了实际风险，而不只是覆盖代码行数。

如果审查失败，先修复问题并重新验证，不得直接进入下一阶段。

## 7. 行为兼容与安全约束

本次任务以结构性重构为主，不默认包含产品功能变更。

必须遵守：

- 不覆盖用户已有的未提交修改。
- 不删除无法证明无用的代码。
- 不随意更改外部接口、持久化格式和配置契约。
- 不改变业务规则、默认值、空值语义和错误处理。
- 不改变必要的异步执行顺序、状态更新顺序和事务边界。
- 不通过捕获并忽略异常来使测试通过。
- 不用 Mock 成功的假象代替真实的数据流验证。
- 不为了让架构图整齐而增加无价值的模块。
- 不批量重命名或格式化无关代码。
- 不自动提交、推送或合并代码。

如果发现现有 Bug，应将其单独记录，分析修复是否会改变既有行为。除非得到明确批准，不要将 Bug 修复与结构性重构混在同一个改动中。

如果缺少测试导致行为兼容无法确认，应明确报告验证缺口，而不是声称重构完全等价。

## 8. 可量化的验收标准

最终验收不以新建了多少文件、减少了多少行代码或采用了多少设计模式为依据。

必须评估以下指标：

### 架构

- UI 不再直接承担不必要的数据访问职责。
- 核心业务规则不再散落于多个无关页面和事件处理器。
- 模块依赖方向清晰，没有新增不必要的循环依赖。
- 共享能力具有明确的职责、归属和调用接口。
- 状态所有权和生命周期有明确约定。

### 抽象质量

- 每个主要抽象都能解释其业务意义和隐藏的复杂度。
- 调用方不需要了解抽象内部的多个实现细节。
- 重复逻辑经过语义验证后再统一。
- 没有仅为假想需求引入的复杂通用框架。
- 不存在大量只有一层转发、却没有隔离价值的包装类。

### 可测试性

- 核心业务规则可以在不启动完整 UI 的情况下测试。
- 数据访问可在需要时通过明确的接口替换。
- 关键业务流程具有行为验证。
- 失败路径、空数据、边界条件及必要的异步行为得到覆盖。

### 兼容性

- 项目构建成功。
- 相关自动化测试通过。
- 重要业务流程的行为与基线一致。
- 所有未解决的兼容性风险都有明确记录。

### 可维护性

- 开发者可以通过目录、接口和文档定位功能的实现位置。
- 新增一个已知类型的功能时，不必修改大量无关模块。
- 修改数据访问方式时，不必同步修改所有 UI。
- 修改业务规则时，不必在多个页面重复修改同一逻辑。

对于无法客观量化的指标，应通过具体案例和代码证据进行验收，不得虚构百分比或改善幅度。
