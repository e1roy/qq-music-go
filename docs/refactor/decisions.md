## D-01 `internal/app` 保持为一个 Go 包，包内按文件分层
- **背景**：MyGo 视图是 `*app` 的方法，直接读状态。
- **备选**：(a) 视图拆成独立包；(b) 每页一个 ViewModel。
- **决定**：保持一个包；用文件职责 + grep 依赖检查分层（target-architecture §4）。
- **理由**：(a)(b) 都要导出或复制大量状态，与 MyGo 惯用法相悖，收益是编译期隔离，但代价是数百行样板。
- **代价**：分层靠约定，需在每次验证中跑检查命令。

## D-02 只为「有不变量、可独立测试」的规则新建包：`playqueue`、`store`
- **理由**：这两块能在不碰 UI 的前提下完整测试，并由编译器保证不依赖 UI。其他规则（音质文字、MRU、谓词）规模小，作为 app 包内纯函数即可。
- **约束**：遵守 AGENTS.md §11.3——只用一次的逻辑不提前抽函数。`qualityLabel` 只用一次，但它是 AGENTS.md §8.7 定义的业务规则，抽出是为了单测，属于「藏着一块复杂东西」的例外。

## D-03 不引入 UseCase 类型
- **理由**：编排操作多为 10-30 行，`*app` 方法已足够；UseCase 类型会让每个操作多一个结构体和构造函数，属于 refactor-playbook.md §4.1 所说的「机械创建大量 UseCase 类」。

## D-04 音源解析用 switch，不用策略接口
- **背景**：已有两种真实来源（QQ、小宇宙），满足 refactor-playbook.md §4.5「已存在多个真实实现」。
- **决定**：在 `playAt` 中按来源 switch（曾提取为 `streamURL`，因只有一个调用方，按 D-14 内联回去）。
- **理由**：两个分支、各 1-3 行；接口 + 两个实现类型会比现在更长。第三种来源出现时再评估。

## D-06 暂不为 `qqmusic.Client` / `xyz.Client` 定义接口（待确认）
- **背景**：refactor-playbook.md §8 要求「数据访问可在需要时通过明确的接口替换」。
- **现状**：离线 UI 测试通过直接设置状态绕过加载；加载编排本身无离线测试。
- **选项**：(a) 暂不定义；(b) 在 app 内为实际调用的约 45 个方法定义一个接口；(c) 按需为个别流程定义小接口；(d) 在 HTTP 层注入假的 `RoundTripper`。
- **建议**：(a)，必要时用 (c)。(b) 是只有一个实现的大接口，正是 refactor-playbook.md 反对的抽象；(d) 需要录制接口响应，维护成本高。
- **影响**：「失败保留旧数据」等加载规则的回归仍需 UI 测试或手动验证。

## D-07 分页状态的统一（已执行，见 D-15）
